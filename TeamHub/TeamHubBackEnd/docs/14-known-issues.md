# 14 · Known Issues & Verified Risks

This is the consolidated index of every **verified** defect, risk, gap and oddity found during the full source analysis. Each row links to the document that contains the evidence (file + line citations live there — nothing is re-argued here). Severity is *my assessment* of the verified behavior, marked **Recommended-grade judgment**, not a claim about original intent. Items whose rationale could not be established are marked *Unknown*.

Categories: **[SEC]** security/authorization · **[DATA]** data integrity/correctness · **[PERF]** performance · **[UX]** user experience · **[QUAL]** code/test quality · **[DEAD]** dead or unreachable code.

## Critical

| # | Finding | Evidence |
|---|---|---|
| C1 | **[SEC]** JWT signing secret is committed in `appsettings.json` and never environment-overridden — anyone with repo access can forge tokens for any user, including `Admin`. | doc 08 §12.1 |
| C2 | **[SEC]** The five public employee read endpoints and two `DepartmentsController` GETs carry `[AllowAnonymous]` — employee directory data is readable without a session. The SPA's `administration.view` permission gates the Administration route but does not protect direct API reads. | doc 12 §3/§11.6, doc 09 §2 |
| C3 | **[SEC/DATA]** Lifecycle **update endpoints bypass the state machine**: `PUT /api/releases\|terminations/{id}` writes `Status` straight to SQL with no `EnsureTransition` and no clearance gate (service `UpdateAsync` is a pure repository pass-through). The status regex accepts all 7 workflow values, so a direct PUT `Status=Released` skips approval edges *and* fires `UPDATE Employees SET IsActive=0`. | doc 12 §7 (Verified bypass), §8 |
| C4 | **[QUAL]** Both backend test projects **do not compile** against current source (stale fakes/DTO shapes after the matrix-paging and permission-keyed refactors), and no CI of any kind exists to have caught it. The suite has silently rotted. | doc 13 §2 (build output captured 2026‑10‑23), §1 |

## High

| # | Finding | Evidence |
|---|---|---|
| H1 | **[SEC]** Permission enforcement differs between SPA and API. `administration.view` gates Administration navigation and route access; `administration.hierarchy.view` gates hierarchy actions; `administration.terminate` or `terminations.add` permits employee-specific termination creation. Employee read API endpoints remain anonymous, so `administration.view` does not protect API reads. `resignations.manage` and legacy `master.view` / `master.manage` remain unused. `RecruitmentsController` remains role-only (`Roles = "Admin"`) with no code. | doc 08 §9, §12.2, doc 09 §2 |
| H2 | **[SEC]** Entra mode is a half-migration: with `enableEntra=true` the interceptor/refresh stack is unregistered and no session bridge exists, so `authenticatedGuard` and every `rbacGuard` instance deny every route — the SPA locks itself out while the backend accepts Entra tokens. | doc 08 §12.11, doc 11 §2/§13 |
| H3 | **[DATA]** *Narrowed 2026-10-26; regressed 2026-10-27 with the succession removal.* `EmployeeReleaseRepository.TransitionStatusAsync` briefly ran the `Released` edge inside one `BeginTransaction`; with the interim-succession gate deleted it is again a non-transactional pair of statements (status update + employee deactivation). Open across the lifecycle: release/termination Create + Update PUTs, release and termination transitions remain non-transactional multi-statement batches, and the pre-transition clearance read still races concurrent edits. Original finding: lifecycle writes were multi-statement batches **without transactions** (INSERT release + deactivate employee; UPDATE transition + deactivate employee). A failure between statements leaves status and `Employees.IsActive` inconsistent. | doc 12 §7.2, §7.5, §11.1 |
| H4 | **[DATA]** Employee create is three non-atomic phases: transactional core write → separate-connection role assignment (implicit `Users` provisioning by email) → separate image write. Partial failure leaves an employee with no account/roles and no compensation path. | doc 12 §5 error path |
| H5 | **[PERF]** The directory grid query returns the cartesian product of employees × addresses × skills × images and deduplicates in C#, then the controller slices in memory — every page request scans the full table set. The departments full-scan and per-leader N+1 hover compound this on the frontend. | doc 12 §3, doc 11 findings |

## Recommended improvements (not existing behavior — labeled per the audit rules)

- **R1** Fix the test projects first (the stale fakes/DTO shapes in doc 13 §2 are mechanical), then add coverage for the workflow classes and `TransitionStatusAsync` gates — the most behavior-dense untested code. *(Recommended)*
- **R2** Remove `[AllowAnonymous]` from employee/master reads or replace with an explicit read-permission policy (addresses C2). *(Recommended)*
- **R3** Route *all* lifecycle status changes — including PUT edits — through `EnsureTransition` + clearance gate, or strip `Status` from the update DTO so only `/status` can change it (addresses C3). *(Recommended)*
- **R4** Wrap lifecycle batches and the employee create saga in transactions / a single Unit-of-Work connection (addresses H3/H4). *(Recommended)*
- **R5** Add a CI step that builds the `tests/` projects outside the `.slnx` (C4 would have been caught by a single `dotnet build` job). *(Recommended)*
- **R6** If Entra is the target, finish the session bridge before flipping `enableEntra` (addresses H2). *(Recommended)*
- **R7** ~~Give `Manager`/`HR` a demo `Users` + `UserRoles` row and add them to `Auth:DevSignIn:AllowedRoles`~~ — **done**: `seed-data.sql` §10 now creates one account per seeded role (Super Admin, Admin, Director, Manager, HR, Developer, IT, Trainee, NormalUser) and the config lists all nine, so every role is signable-in. §11 also grants `profile.view`/`profile.edit` to every role and mirrors Admin's grant set onto Super Admin. Still open from the original item: retire the six inert codes with `UPDATE Permissions SET IsActive = 0`. *(Recommended)*

## Explicitly unverified / limited

- Frontend `ng test --watch=false` **was** executed (re-run 2026-10-23 after the login change detection fix): 10 files / 63 tests, 62 passed, 1 pre-existing failure (`employee-lifecycle-form.spec.ts:56`); `ng build --configuration development` succeeds (initial 3.91 MB) and the production build fails only on two pre-existing budgets (initial bundle 1.25 MB vs 1 MB; `employee-lifecycle-list.css` 9.40 kB vs 8 kB). No lint target exists. Details in doc 13 §5.
- The **backend was compiled but not restarted**: `dotnet build` of `TeamHub.API` succeeds (0 errors, built to `.tmpbuild` because the running host locks its own output), yet the process serving `localhost` still runs the pre-`terminations.add` assembly — the new policy takes effect only after a restart. *Verified* against the live database and over HTTP (seed batches applied and re-run for idempotency; `dev-sign-in` returned the expected `resignations.add` claim set and a termination `POST` with that token returned 403).
- A **browser session was driven on 2026-10-23** against the running dev server and API, proving the "Add" buttons follow their own codes: with Admin's `terminations.add` stripped from the stored claim string the "+ New Termination" button disappears while the list still renders (its `terminations.view` untouched) and the People row's "Terminate" action goes with it; `resignations.add` removed independently hides only "+ New Resignation"; re-signing in restores both; `NormalUser` (single code `resignations.add`) sees exactly `People` + `Apply Resignation` in the navigation and is redirected away from `/employees/terminations`. The claim-string surgery was client-side only — the API-side effect of a revoked code is *not* covered by this, since the running assembly still has the `Admin` role bypass.
- Other runtime behavior (image files on disk, concurrent lifecycle writes) was not exercised; remaining claims are static-analysis + build-run evidence.
- Original design intent is marked *Unknown* wherever the code gave no rationale (L2, L6, M6, L15, Entra half-migration).
- The menu was verified by unit tests over the pure filter and the component tree, and — for the resignation/termination entries — by the live browser pass described above.
