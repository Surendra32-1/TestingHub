Topic	Guidance
Purpose	Complete TeamHub manual test pack: 124 frontend cases, 236 backend API cases, 25 database cases and 22 permission cases, all written against the current code and schema.
Sheets	Read Me (this sheet), Frontend Tests (UI behaviour and guards), Backend API Tests (controllers, payloads, ProblemDetails), Database Tests (constraints, keys, soft delete, audit), Permission Tests (policy enforcement and UI visibility), Defect Log (raise one row per failure).
How to run	Backend: start TeamHub.API in Development with Entra disabled and use POST /api/auth/dev-sign-in to obtain a token per role. Frontend: npm start, open http://localhost:4200, and use the development account picker on /login. Database: run the scripts in TeamHub.Infrastructure (authentication-schema.sql, databasesesign.sql, rbac-schema.sql, seed-data.sql) against a disposable database.
Placeholders	Anything inside angle brackets must be replaced before execution: <ADMIN_TOKEN>, <NORMAL_USER_TOKEN>, <EMPLOYEE_ID>, <DEPARTMENT_ID>, <today>, <RELEASED_ID>, <PERMISSION_ID>. Access tokens live 15 minutes; refresh them between groups.
Result columns	"Expected Result holds the assertion. On the Backend API Tests sheet the Actual Result, Status, Executed By and Execution Date columns carry real observations from the 2026-10-30 run against TeamHub.API (188 Pass, 2 Fail, 46 Not Run of 236 cases); the failures are DEF-001 (refresh-token HTTP 500). On the Frontend Tests sheet the same four columns carry real observations from the 2026-10-30 browser run against http://localhost:4200: 23 of 124 cases were driven in headless Chrome through CDP (18 Pass, 5 Fail), and its five failures are DEF-002 to DEF-006. The other 101 cases still read ""Not executed."" because no browser check has been recorded for them yet, and the Database and Permission sheets have no run at all. Failures are cross-referenced to the Defect Log sheet instead of a Defect ID column, because these sheets keep the original template column set."
Frontend execution record	"23 of 124 cases (FE-058, FE-066-FE-087) were executed against the running SPA: the real Angular 20 application on http://localhost:4200 with the real TeamHub.API on http://localhost:5169 and the seeded database, driven by Chrome DevTools Protocol with trusted mouse clicks, key presses and real file selection, so every result is read back from the rendered DOM or the captured network traffic. Executed By reads ""Automated browser runner"" and Execution Date reads 2026-10-30 on those rows only. The remaining 101 cases are deliberately left as Not Run with ""Not executed."" - they are ready to run and are not blockers."
Status values	Pass, Fail or Not Run only. The Status dropdown in every sheet rejects any other value, so do not type Blocked - note the blocked precondition in Actual Result and leave Status as Not Run.
Priority	P1 = release blocking, P2 = important behaviour or validation, P3 = edge case or cosmetic.
Defect handling	When a case fails, add a Defect Log row, cross-reference the test case id and keep the failure evidence (request id, screenshot, SQL result) in Actual Result.
Known gaps captured as cases	Missing Origin requirement on cookie endpoints, no access-token denylist after logout, /api/employees/employee-master without a policy, empty 401/403/404 bodies (BE-229 to BE-231), and the frontend menu checking organization.* codes while the API checks master.*. These cases are marked P2/P3 or flagged in the expected text. Edit this line if the team decides to accept the risk instead of fixing it.
