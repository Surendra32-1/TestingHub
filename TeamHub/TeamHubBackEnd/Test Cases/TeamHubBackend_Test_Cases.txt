Topic	Guidance
Purpose	Executable backend API test suite for TeamHub (236 cases, BE-001 to BE-236). Every case targets a real controller action, payload and validation message taken from the current source.
Coverage	Authentication and session (dev sign-in, refresh rotation, logout), self-service profile PATCH whitelist, people search, employee administration and public directory, organization tree and hierarchy CTE, resignations and terminations workflows with clearance gates, RBAC catalog and matrices, 15 master-data modules, and cross-cutting error-envelope behaviour.
How to run	1) Start TeamHub.API with ASPNETCORE_ENVIRONMENT=Development and Auth:Entra:Enabled=false against a disposable TeamHub database. 2) Sign in through POST /api/auth/dev-sign-in to obtain an access token per role. 3) Execute each case and record Pass or Fail plus the executed-by and date columns.
Placeholders	Anything inside angle brackets must be replaced before execution: <ADMIN_TOKEN>, <NORMAL_USER_TOKEN>, <EMPLOYEE_ID>, <DEPARTMENT_ID>, <today>, <RELEASED_ID>. Tokens are short-lived (15 minutes), so refresh them between groups.
Test data	Use the seed script (seed-data.sql) plus one disposable employee per run. Never test against production data; soft-deleted rows must be purged between cycles.
Expected result	Success cases assert the ApiResponse envelope (success, message, data) with the exact message text. Controller and model-binding failures assert the RFC 9110 ProblemDetails extensions (success, message, data, error, errors). Framework-level 401/403/404 responses carry no body - see the known-gaps row.
Execution record	Executed 2026-10-30 against TeamHub.API on http://localhost:5210 (ASPNETCORE_ENVIRONMENT=Development, Entra disabled, seed database restored after the run). 190 of 236 cases were driven as real HTTP requests: 188 Pass, 2 Fail, 46 Not Run. Not Run means the case needs a token, host configuration or record that this seed cannot produce; the exact reason is written in its Actual Result.
Defects raised	DEF-001 affects BE-012 and BE-017: POST /api/auth/refresh-token returns HTTP 500 for any request that carries a valid cookie. Dapper cannot materialise AuthRepository.RefreshSessionRow because the record declares DateTimeOffset ExpiryDate and DateTimeOffset? RevokedDate while dbo.RefreshTokens stores datetime2, so GetRefreshSessionAsync throws InvalidOperationException before rotation. Token refresh is therefore completely broken; the negative cases (BE-013, BE-015, BE-016) still pass because they are rejected before the session is read.
Result columns	Expected Result states the assertion to check (message text, status, side effect). Actual Result holds the observed HTTP status and response body from the executed run, or the reason a case could not be run. Defect ID stays N/A unless Status is Fail.
Status values	Pass, Fail or Not Run only. The Status column carries a dropdown that rejects any other value, so do not type Blocked - record a blocked precondition in Actual Result and leave Status as Not Run.
Priority	P1 = release blocking core path, P2 = important behaviour or validation, P3 = edge case, cosmetics or documented gap.
Known gaps captured as cases	Missing Origin requirement on cookie endpoints, no access-token denylist after logout, /api/employees/employee-master without a policy, empty 401/403/404 bodies because no OnChallenge or UseStatusCodePages is configured (BE-229 to BE-231), and the mixed soft-delete visibility between master repositories (BE-235, BE-236). Treat these as accepted risks or raise defects - do not record them as Pass without a decision.
